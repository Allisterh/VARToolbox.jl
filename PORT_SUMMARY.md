# VAR Toolbox → Julia: port summary

A record of what was ported, how it was verified, what the exercise turned
up about the MATLAB original, and what remains.

**Branch:** `julia-port` (15 commits, not merged to `main`).
**Package:** `julia/VARToolbox/`.
**Nothing under `v3dot1/` or `v3dot0/` was modified.**

---

## 1. Outcome

The estimation and inference pipeline of Ambrogio Cesa-Bianchi's VAR Toolbox
v3.1 is ported to Julia and validated against the MATLAB original.

| | |
|---|---|
| Tests passing | **1,741**, from a clean clone, with no MATLAB licence |
| Julia source | 12 files, ~3,190 lines, plus the plotting extension (3 files, ~580 lines) |
| Julia tests | 10 files, ~2,060 lines |
| MATLAB fixture generators + shims | 14 files |
| Golden-master fixtures | 8 `.mat` files, 6.3 MB, committed |
| Exported API | 74 symbols |
| Replication figures | 12 PDFs in `examples/figures/`, regenerated from the port |
| Derived from | upstream `ambropo/VAR-Toolbox` @ `7695feb` (115 `.m` files, 11,417 lines) |
| Licence | GPL-3.0, inherited; attribution carried in every file header |

All four published replications shipped with the toolbox reproduce against
the same `.xlsx` data files the MATLAB scripts read:

| replication | identification | agreement with MATLAB |
|---|---|---|
| Stock & Watson (2001, JEP) | recursive | `rtol = 1e-10` |
| Blanchard & Quah (1989, AER) | long-run restrictions | `rtol = 1e-10` |
| Uhlig (2005, JME) | sign restrictions | `rtol = 1e-10` |
| Gertler & Karadi (2015, AEJ) | external instrument | `rtol = 1e-6` ¹ |

¹ Not a porting discrepancy. That specification fits 49 coefficients on 384
persistent monthly observations, giving `cond(X'X) ≈ 2.2e9`; solving through
the normal equations admits ~`5e-7` relative error in *any* implementation.
The measured difference is `6.5e-8` — an order of magnitude inside the
bound. The test asserts `cond(X'X) > 1e8` alongside, so the justification is
self-checking: if the design ever became well conditioned, the loosened
tolerance would stop being warranted.

**The plotting layer is ported too** (Phase 8), as the package extension
`ext/VARToolboxPlotsExt/` — it activates on `using Plots`, so core
estimation never loads a plotting stack. Every figure the MATLAB toolbox
produces for the four replications is regenerated by
`examples/figures.jl` into `examples/figures/` from the *recorded* MATLAB
draws, so each curve is numerically identical to a MATLAB run — a fresh
MATLAB R2026a run asserted bit-equality against the same fixture and
rendered the same 12 figures for a side-by-side visual comparison. The
fidelity target is v3dot1's plot code with v3dot0's `quality==2` save
branches restored, because v3dot1 dropped them while defaulting
`quality = 2`: the stock v3dot1 plot layer silently saves nothing.
Rendering deviations (marker glyph, legend geometry, fonts) are listed in
`PORTING_LOG.md` ("Phase 8").

## 2. What "validated" means here

This is the part of the exercise with the most methodological content, so it
is worth being precise about.

### Golden masters, not a green test suite

Every function is compared elementwise against output dumped from MATLAB
R2026a on fixed inputs, at `rtol = 1e-10` unless a written justification
says otherwise. Fixtures and the MATLAB scripts that generate them are both
committed, so the suite runs without a MATLAB licence while remaining
regenerable.

### Bootstrap and sign restrictions are exact, not distributional

The original brief assumed cross-language RNG parity was impossible and
prescribed comparing summary statistics over ~10,000 draws at 1–2% relative
tolerance.

**That tolerance would have been wider than a real defect it needed to
catch** — see §4.1 — and would have passed a build in which every error band
used the wrong quantile definition.

The stochastic surface turned out to be only 8 call sites across 5 files,
each drawing an iid block up front. So instead: four *recording shims* under
`test/fixtures/gen/shim/` — copies of upstream files whose only change is
routing their `randn`/`rand` calls through a wrapper that saves each draw
(`diff` confirms two or three changed lines each; `make_shim.py` regenerates
them in byte mode so the audit trail survives). Replaying those draws in
Julia makes the entire bootstrap and sign-restriction pipeline an **exact**
comparison at `1e-10`.

A side benefit: `VARToolbox.jl` is reproducible and safely parallelisable
through an explicit `rng` argument. The MATLAB original is neither.

### Replications are checked for economic content, not just agreement

Agreeing with MATLAB proves the port faithful, not that either is correct.
Each replication therefore also asserts its identifying restriction actually
binds:

- **Stock-Watson** — a funds-rate shock moves neither unemployment nor
  inflation on impact; every row of Table 1.B sums to 100.
- **Blanchard-Quah** — the cumulated GDP response to the demand shock dies
  out (under 2% of its own peak at horizon 40) while the supply response
  does not (over 50%). This is the paper's identifying assumption, tested
  rather than assumed.
- **Gertler-Karadi** — IV and recursive responses differ materially, so the
  instrument is doing work.
- **Uhlig** — every accepted draw satisfies the imposed sign pattern.

Similarly, `ident = "iv"`'s dependence on variable ordering is proved
load-bearing by a test showing that reordering `ENDO` changes the answer.

## 3. Design decisions

Three decisions were signed off before any code was written; all three touch
every downstream file.

**D1 — MATLAB-verbatim function names, suffixed type names.** `VARmodel`,
`VARir`, `SR` keep their names so the existing manual and Primer slides
transfer directly. Types become `VARModel`, `VAROptions`, `SROutput` — if
the type were named `VAR`, the idiomatic `VAR = VARmodel(...)` would shadow
it and make the constructor unreachable for the rest of the scope.

**D2 — Replicate upstream behaviour, document it, pin it with a test.** No
silent improvement. Four places deviate deliberately, each because upstream
always crashes there (§4.2); every one is documented and its contract still
tested.

**D3 — Options structs are immutable, updated with `@set`.** Not a stylistic
choice. MATLAB passes structs by value and the toolbox *relies* on it:
`SR.m` sets `VARopt.ident = 'sign'` and `SignRestrictions.m` sets
`VARopt.nsteps = VARopt.sr_hor` on their local copies. A mutable Julia
struct would leak both back to the caller, silently corrupting every band
and plot computed afterwards. Immutability makes that failure impossible.

One rename was forced by the language: `const` is reserved in Julia, so
`VAR.const` → `VAR.constant` and `HD.const` → `HD.constant`.

## 4. What the port found in the MATLAB original

Verifying line by line against a reference implementation surfaces things
reading alone does not. These are grouped by what they mean for someone
using the toolbox to produce results.

### 4.1 Silently affects results

**`prctile` is the Hazen (type-5) quantile.** Julia's default `quantile` is
type 7. At `pctg = 95` — the toolbox's own default — the two differ by
percent-level amounts. Any port, replication, or cross-check in another
language must match MATLAB's definition or every error band is quietly
wrong. A test asserts the naive translation does *not* match, so this cannot
regress.

**`SR` returns `IR`, `VD` and `HD` computed from a different draw than the
`B` it returns alongside them.** `SR.m` labels each stored draw by the
accepted count *before* incrementing it, so accepted draw `k` is filed under
`draw(k-1)`, while the final lookup uses `sel` indexed into `Ball`.
Demonstrated on Stock-Watson data with `sr_mod = 0`: `SRout.B` was accepted
draw 24 and `SRout.IR` matched draw 25 to `0.0e+00`. Anyone plotting
`SRout.IR` beside `SRout.B` is looking at two different rotations. There is
also a latent crash when `sel == ndraws`, since that label is never created
— probability roughly `1/ndraws` per call. The port replicates this by
default and offers `fix_draw_index = true` for the corrected behaviour.

**`IR` and `VD` are indexed differently.** `IR` is
`(nsteps × nvar × nshocks)`; `VD` is `(nsteps × nshocks × nvar)` — the last
two dimensions transposed. Verified numerically: `sum(VD[h,:,k]) == 100` for
every horizon and variable, while summing the third index does not.
`HD.shock` follows `VD`'s convention. `CLAUDE.md` previously asserted the
two matched; that has been corrected.

**`LPmodel`'s reported bands cannot be reconstructed from its reported
standard errors.** `bstd_HW` is assigned twice in consecutive statements,
the second from `OLSout.bstd_NW`, so the field named for White errors holds
Newey-West ones. Meanwhile `INF`/`SUP` are computed from the *White* errors.
Separately, the bands are asymptotic Normal with no correction for the
serial correlation that overlapping horizons induce by construction, so they
are anti-conservative at longer horizons.

**`VARhd`'s exogenous contribution ignores lags of the exogenous
variables** — it uses only the contemporaneous coefficient, so with
`nlag_ex > 0` the decomposition does not reconstruct the data.

### 4.2 Blocks usage outright

**`OLSmodel`'s `const == 3` always fails.** It prepends two columns
(`[ones trend.^2]`) but increments the coefficient count by three, so the
normal-equations inverse is built at the wrong dimension. Note also that
`VARmakexy`'s `const == 3` prepends *three* columns — the two functions
disagree about what `3` means.

**`LPoption.m` defines neither `nlag` nor `const`, but `LPmodel.m` reads
both** on its 8th and 9th lines, so calling `LPmodel` with an unmodified
options struct dies on a missing-field access. The file's own guards for
exactly this (`if ~exist('nlag','var')`) are dead code — the variables were
assigned two lines earlier.

**`LPmodel`'s `EXOG`/`LAGS` dimension checks are unreachable**, nested inside
another check and placed after its `error(...)` call.

In these three cases the port raises a descriptive error instead of
reproducing a guaranteed crash — the only deviations from D2, all documented.

### 4.3 Wrong, lower impact

- **`CommonSample`'s `lo` is not the trailing-NaN count.** Its loop never
  stops at the first non-NaN, so it counts every NaN row outside the leading
  run. Coincides with the documented meaning only when the data has no
  interior gaps — which is true of the toolbox's own fixtures, presumably
  why it went unnoticed.
- **`nanmedian` converts an exactly-zero median to `NaN`.**
- **`nanmovavg` returns all-`NaN` for every input** — its inner loop reads
  the output array instead of the input. Not ported.
- **`tdis_inv` loses about seven digits near `p = 0.5`**: `beta_inv` stops at
  a ~`1e-14` Newton residual and the final `sqrt` amplifies it.
  `tdis_inv(0.5, 10)` returns `3.2148e-07` where the exact answer is `0`.
  Harmless in the tails, so `OLSmodel`'s confidence intervals are unaffected.
- **`SignRestrictions` does not raise when it exhausts `sr_rot`** — its error
  path is commented out; it returns `[]` silently. Only `SR`'s separate
  `sr_draw` budget raises.
- **`MovAvg` and `MovAvgCent` disagree on two conventions at once**: `window`
  is a total length in one and a half-width in the other, and one propagates
  NaN while the other skips it.
- **`CorrTable` fails to blank an exactly-zero upper-triangular entry**,
  because `find(triu(...))` returns only non-zero elements.

### 4.4 Documentation errors

- `VARmodel`'s docstring says `const` defaults to `0`; the code uses `1`.
- `VARir.m`'s header and `VARoption.m`'s comment both document four
  identification schemes; the code implements five (`exog` exists in `VARir`
  only, and `VARvd`/`VARhd` reject both `iv` and `exog`).
- `L`'s sign convention is inverted relative to its name: a *positive*
  argument produces a *lead*.
- `Utils/columns.m` declares `function c = cols(DATA)` — filename and
  function name disagree.

### 4.5 Practical gotchas

- **`GO_GK2015.m` applies `Num2NaN` before selecting columns.** The sheets
  encode missing values as the sentinel `123456789` and the `ff4_tc`
  instrument covers only part of the sample; skipping this step leaves
  sentinels in the instrument and makes the IV first stage numerically
  singular (`RCOND ≈ 1.5e-16`).
- **Every `Replic/*/GO_*.m` opens with `clear all`**, which wipes the
  workspace of any driver script that loops over them. Fixture generators
  are written as functions for this reason.
- **Three of the four replications die at their final `SaveFigure(...,1)`
  call**, which routes to the `export_fig` that `v3dot1` no longer ships.
  All numerical output is produced before the failure.
- **Never run `restoredefaultpath` through the `matlab` MCP server** — it
  removes the helpers the server injects, and the session cannot be repaired
  in place. (Learned the hard way; now recorded in `CLAUDE.md`.)

## 5. What remains

Stated plainly rather than left implicit. Everything the VAR pipeline itself
depends on is ported and validated; what is listed here is peripheral.

| item | size | status |
|---|---|---|
| `Figure/` leftovers | 6 files | The plotting layer landed in Phase 8 (`ext/VARToolboxPlotsExt`): the six `VAR/*plot` functions plus `PlotSwathe`, `AreaPlot`, `cmap`, `DatesPlot`, `FigSize`, `SaveFigure`. Still unported: `BarPlot`, `PlotLine` (broken upstream — calls a function that exists nowhere in the repo), `PlotStatesShaded`, `pantone`, `LegPlot`, and `cmap`'s parula tail. None is used by any toolbox figure. |
| Text-table printing — `VARprint`, `OLSprint`, `ARDLprint`, `TabPrint`, `mprint`, `roundnum2cell` | ~900 lines | Display-only; produces no number any downstream calculation consumes. |
| `SummStats` + `adf` + `ztcrit` | ~340 lines | Needs an augmented Dickey-Fuller routine with a hardcoded critical-value table, plus `skewness`/`kurtosis`. Independent of the VAR pipeline. |
| `Stats/*Unbalanced`, `CrossWeightAverage` | ~400 lines | Alternative NaN-handling paths over statistics already ported. |
| Assorted `Auxiliary/` utilities | — | Either plotting-layer or unreferenced by the core call graph. |

**Coverage gaps inside what *is* ported**, for honesty:

- The `maxEig ≥ 0.9999` resample-and-retry branch in the band functions is
  never deliberately triggered by a fixture.
- `VARvdband` is not tested with an exogenous variable.
- `LPmodel` is not tested with a multi-column `S`.
- `VARdrawpost`'s sampling path is checked only for shape and symmetry; its
  distributional correctness is not asserted, though the deterministic
  computation downstream of the draw *is* validated exactly by injection.

**A note on Statistics Toolbox dependencies.** The brief catalogued
`VARdrawpost` alone. The real surface is wider: `prctile` in `SR`,
`VARirband`, `VARvdband`, `censor` and `winsor`; `norminv` and `zscore` in
`LPmodel`; `skewness`/`kurtosis` in `SummStats`; `corr` in several `Stats/`
functions. Conversely, `Auxiliary/`'s distribution functions are hand-rolled
on base MATLAB's `betainc` and need no toolbox at all.

## 7. Three caveats about this summary

**The brief itself was wrong in places, and was corrected first.** The
starting brief (`JULIA_PORT_PROMPT.md`) was written by another agent. Auditing
it against the working tree found four factual errors — most consequentially
that `VARvd`/`VARhd` support all five identification schemes, which they do
not — plus a validation tolerance that would have masked a real defect. It
was rewritten as revision 2 before any code was written. Anyone reading the
brief should read revision 2, not the original.

**One error in this work was caught only after it was first reported
finished.** The fixture manifest originally used a single SHA-256 over file
bytes, documented as making generator drift detectable. It does not: MATLAB
stamps a creation timestamp into every `.mat` header, so the byte hash
changes on any regeneration regardless of content. The check ran green
throughout — it simply was not checking what the documentation claimed.
Fixed by adding a canonical hash over the data, verified stable across
regeneration, with six negative tests to stop it passing vacuously. The
episode is recorded in `PORTING_LOG.md` rather than quietly patched, because
a validation harness that overstates what it verifies is the failure mode
this whole exercise exists to avoid.

**The Uhlig "replication" did not replicate the paper's settings until the
figure comparison caught it.** The Phase 6 fixture generator — and the Julia
replication that mirrors it — silently left `sr_hor` and `pctg` at their
defaults (1, 95) where `GO_Uhlig2005.m` sets 6 and 68. Both languages
agreed with each other to `1e-10` throughout, so no numeric test could
catch it: the port was exactly faithful to a *variant* of the paper. The
first MATLAB-vs-Julia figure overlay made the too-wide bands obvious in
seconds. Fixed on both sides, fixture regenerated (all non-Uhlig fields
verified bit-unchanged), and recorded in `PORTING_LOG.md` ("Phase 8") —
a concrete argument for figure-level replication as a validation layer,
not a cosmetic afterthought.
